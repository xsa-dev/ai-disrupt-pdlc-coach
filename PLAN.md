## 1. Vision & Final Goal

**Цель:**

Создать **внутренний Telegram-инструмент «Disrupt PDLC Coach»**, который выступает в роли **коуча и фасилитатора** для инженерных команд.

Агент помогает командам **системно проходить трансформацию разработки** по методологии AI-Disrupt PDLC: от честной диагностики текущего состояния до конкретных изменений в процессах, среде исполнения, ролях и контуре управления с целью движения к уровням L4–L5.

### Ключевые характеристики инструмента
- Ведёт **полные end-to-end сценарии** (диагностика → план → проектирование → внедрение → сопровождение).
- Работает через **Telegram** как основной интерфейс.
- Поддерживает **несколько команд** с отдельным контекстом, историей и артефактами.
- Выдаёт **структурированные артефакты** (отчёты, roadmap, чек-листы, спецификации, рекомендации).
- Жёстко опирается на принципы книги: «Среда важнее модели», двухпетлевая модель, Governance Mesh как третья ось, Zero Friction, Evidence Bundle и т.д.
- Со временем легко обогащается внутренними кейсами, антипаттернами и практиками организации.

**Девиз:** Не просто «знает книгу» — помогает командам **применять** методологию на практике и двигаться вперёд.

## 2. Основные принципы из книги (должны быть вшиты в агента)

1. **Среда работы ИИ-агентов важнее модели** (самый важный принцип).
2. **Человек** — субъект петли намерения. **ИИ-агент** — субъект петли реализации.
3. **Контур управления (Governance Mesh)** — третья ось PDLC, работает в реальном времени.
4. **Валидация встроена**, а не добавлена (Evidence Bundle, агент-ревьюер).
5. **Исследование перед генерацией** (Discovery с измеримой гипотезой результата + PR/FAQ).
6. Честная оценка зрелости важнее «подталкивания» к высоким уровням.
7. Сложные мультиагентные оркестрации экономически оправданы только после устойчивого результата на одном агенте.

Агент **никогда** не должен рекомендовать менять модель вместо улучшения среды.

## 4. Ключевые End-to-End Сценарии

### Сценарий 1: Диагностика зрелости команды (Рекомендуемый первый)
**Вход:** Команда отвечает на структурированные вопросы.  
**Процесс:** 
- Оценка по шкале L0–L5 (организационная зрелость).
- Оценка по R0–R5 (автономия агентов).
- Оценка горизонта задач (task horizon).
- Выявление сильных/слабых сторон по принципам книги.
**Выход:**
- Структурированный отчёт (Markdown + таблица).
- Текущий уровень + обоснование.
- Рекомендации по ближайшим шагам.
- Сохранение в профиль команды.

**Gate-критерии переходов** (из книги) должны использоваться при диагностике.

### Сценарий 2: Построение Roadmap трансформации
**Вход:** Результат диагностики или ручной ввод текущего уровня + желаемый.  
**Процесс:** 
- Определение целевого уровня (реалистичного).
- Разбиение на этапы (с временными горизонтами из книги).
- Определение ключевых практик, которые нужно внедрить на каждом этапе.
- Учёт Governance и валидации на каждом шаге.
**Выход:** 
- Roadmap в табличном/списочном виде.
- Приоритетные практики.
- Риски и антипаттерны.

### Сценарий 3: Проектирование/улучшение конкретного элемента
Примеры элементов:
- Среда работы агентов (harness).
- Guardian Agents.
- Контур управления / Governance Mesh.
- Роли в команде.
- Методика валидации и Evidence Bundle.
- Discovery-процесс.

### Сценарий 4: Аудит текущих практик
Команда присылает описание текущих процессов. Агент выдаёт аудит-отчёт с соответствием принципам, найденными антипаттернами и рекомендациями.

### Сценарий 5: Сопровождение трансформации (long-running)
Регулярные сессии: обновление статуса по roadmap, проверка прогресса, корректировка плана.

## 14. Приложения

### 14.1 Уровни зрелости команды L0–L5 (из книги)

**Важно:** L0–L5 — это уровень зрелости **команды**, а не отдельного агента.

| Уровень | Состояние                              | Медианный горизонт задачи       | Валидация                          | Примечание |
|---------|----------------------------------------|----------------------------------|------------------------------------|----------|
| L0      | Нет устойчивой ИИ-практики             | Нет агентных задач               | Нет требований                     | - |
| L1      | Эксперименты с IDE-плагинами           | Минуты (автодополнение)          | Не требуется                       | - |
| L2      | Первые инженеры используют ИИ для рутинных задач | До 30 минут             | AI-gate в CI                       | SDD-lite |
| L3      | SDD внедрён; агенты кодирования работают в ветках под ревью | До 2 часов          | Агент-ревьюер + Evidence Bundle    | Обязательный SDD |
| L4      | Параллельное выполнение, мульти-сессии | До 4 часов (на зрелом уровне до 1 рабочего дня) | Интегрированная методика валидации | Long-Running Runtime |
| L5      | Скоординированные команды агентов (Coordinated Agent Teams) | Длительные задачи (несколько дней) | Объяснимость в реальном времени + полный цикл ADLC | Требует платформенной команды |

**Gate-критерии переходов (основное):**
- L0 → L1: Доступ к IDE + базовая гигиена промптов.
- L1 → L2: SDD-lite, AI-gate в CI, первые evals.
- L2 → L3: Обязательный SDD, агент-ревьюер, Evidence Bundle.
- L3 → L4: Среда долгосрочных процессов + библиотека паттернов + методика валидации.
- L4 → L5: A2A + скоординированные команды агентов + объяснимость в реальном времени.

### 14.2 R0–R5 (риск-адаптивная лестница автономии агента)

- **R0**: Только подсказывает.
- **R1–R2**: Ограниченная автономия с обязательными подтверждениями.
- **R3–R4**: Более высокая автономия в очерченных областях.
- **R5**: Работает автономно в чётко ограниченном домене.

Класс R определяет guardrails, политику подтверждений и требования к Guardian Agents.

### 14.3 Четыре архитектурных принципа

1. Среда работы ИИ-агентов важнее модели.
2. Исследование перед генерацией.
3. Валидация встроена, не добавлена.
4. Контур управления — третья ось PDLC (работает в реальном времени).
